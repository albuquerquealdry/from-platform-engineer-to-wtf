Part 4 ended with a benchmark that looked good and a nagging feeling: every app we
generated looked like the *same* app. Dark zinc background, indigo accent, forever.
This entry is about finding out why by reading the market leader's leaked agent
prompt against ours, and shipping the three upgrades that came out of that reading:
a design system that is born per app, a first-impression protocol (which failed
spectacularly before it worked), and a component kit mature enough that the agent
stopped inventing UI.

## The diagnosis: we had a theme, they have a system

We assumed the leader's secret was a beautiful fixed theme. The leaked prompt says
the opposite, in capital letters: *"The design system is everything... never write
custom styles in components... USE SEMANTIC TOKENS... DO NOT use direct colors like
text-white, bg-white."* Their agent doesn't inherit a look; it **writes the look
first** — a palette, gradients, shadows, as CSS tokens — and then composes
components that only ever reference tokens.

Our prompt did the exact opposite. It instructed raw utility classes (`zinc-800`,
`indigo-600`) as the path to "pretty". That guaranteed consistency and killed
identity: one theme to rule every app, whether you asked for a finance dashboard
or a kids' birthday invitation.

## Architecture: identity as a single source

The fix is one level of indirection, old as design systems themselves, wired into
the workspace template:

<Mermaid
  caption="One edit point: the agent themes the :root block; everything downstream follows."
  chart={`
flowchart LR
  REQ[User request] -->|sets the mood| ROOT[":root tokens<br/>(HSL palette, gradients,<br/>shadows, radius)"]
  ROOT --> THEME["@theme inline<br/>(Tailwind v4 bridge)"]
  THEME --> UTIL["semantic utilities<br/>bg-primary, text-foreground,<br/>bg-surface, border-border"]
  UTIL --> KIT["component kit<br/>Button, Card, Dialog, Toast..."]
  KIT --> PAGE[generated pages]
  style ROOT fill:#2d1f47,stroke:#8b5cf6
`}
/>

The template's `globals.css` now opens with a `:root` block of semantic tokens in
HSL, bridged to Tailwind v4 utilities via `@theme inline`. The agent's system
prompt flipped from "use these classes" to a golden rule: **define the tokens for
THIS app's theme before writing any page; raw color in a component is forbidden**.
The code reviewer got the matching lens: a raw Tailwind palette class in a
component now fails review like a bug does.

The acceptance test was the fun part. Same frozen benchmark prompt, plus a second
prompt engineered to be its temperamental opposite. Same system prompt, same
model, same template:

![The finance dashboard: deep navy tokens, cyan accent, sober — the agent chose :root values to match the domain](/log-005-identity-finance.png)

![The kids' party invite: deep purple background, pink-to-orange gradient hero, warm cream text — a different :root, nothing else changed](/log-005-identity-party.png)

Zero raw colors in either (we grep the generated files; the reviewer also hunts
them). The identity now comes from the request, not from the template.

## The first-impression protocol, and the day the agent answered with a plan

The leaked prompt treats the first message of a project as a product moment:
*"make sure to wow them with a really, really beautiful and well coded app."* It
injects a whole extra block only on that first message — what the request evokes,
design inspirations, a deliberately small feature list, palette and motion — and
expects implementation in the same turn.

We ported the idea: a registry-managed prompt block that the worker attaches to
the builder's task only when the project has no prior messages. First real test, a
Masonic lodge's institutional site: the agent **replied with the plan and built
nothing**. The chat got a beautiful paragraph about "discreet tradition,
aged-gold accents, inspirations from historic clubs"; the preview stayed on the
template's empty page. The protocol told the model to think before coding, and the
model delivered the thinking as the deliverable.

Two fixes, one per layer:

1. **Prompt**: the block now states the reasoning is internal — *think silently,
   never deliver the plan as the answer; finishing without writing files is
   failure*. (The leaked prompt has this exact defense; now we know why.)
2. **Structure**: the orchestrator gained a guard — a first generation that ends
   with zero files written triggers one corrective round that feeds the agent its
   own plan and demands implementation. Even if the model slips, the harness
   doesn't.

Second attempt, new project, same request:

![First generation under the vitrine protocol: gold CTA, ceremonial eyebrow, contact card — and the plan stayed internal](/log-005-lodge-hero.png)

The protocol fired once (logged), the corrective guard was never needed, and the
page arrived composed: hero with badge, history section, three pillars, a session
calendar with degree badges, contact form.

<Callout type="broke">
  A prompt that says "think before you code" will, some percentage of the time,
  produce a model that thinks instead of coding. Instructions alone don't fix
  this reliably — the leaked prompt's "first message = just write code" line
  exists because they hit it too. Pair the instruction with a structural check
  the model can't talk its way past.
</Callout>

## The kit grew up

Part 4's hand-made kit (seven components) proved that composition beats invention.
It also had a ceiling: no dialog, no toast, no tabs — so every time a request said
"a button that opens a form", the agent improvised an inline form, and our visual
critic kept flagging it. The upgrade: the template now ships Radix-based
primitives — Dialog, Tabs, DropdownMenu, Tooltip, Sheet, Skeleton — plus a themed
toast, all consuming the same tokens. When the agent themes the `:root`, the
modal and the toast change clothes with the rest of the app.

The prompt gained an intent-to-component map instead of adjectives: a creation
form opened by a button IS a Dialog; an action confirmation IS a toast; a loading
state IS a Skeleton. And the leaked prompt's customization rule came along:
variants built from tokens, never class overrides.

## The critic earned its keep, again

The strongest moment of the week wasn't aesthetic. On the lodge project we sent a
tiny follow-up — *"change the time to 13h00"* — and the builder updated the
calendar list but missed the main highlighted time. The code reviewer approved:
the code is consistent, nothing smells. The Designer looked at the **screenshot**
and wrote: *"the main time was not updated to 13h00."* One refine round later it
shipped correct.

![The lodge calendar after the fix: four sessions, degree badges, 13h00 everywhere — the miss was caught by an agent looking at pixels](/log-005-lodge-calendar.png)

<Callout type="learned">
  We built the visual critic to police beauty. It turned out to police
  *truth* — whether the pixels match the request — which code review structurally
  cannot see. A text-only reviewer approves a lie that renders; a critic with
  eyes does not.
</Callout>

## Observability grew with it

Two quality-of-life upgrades landed alongside: every execution now propagates a
**session id** (one session per project — the whole conversation of an app, with
accumulated cost, in one Langfuse view), and the Designer's critique became a
named span with its verdict and prompt version, instead of an anonymous
ChatCompletion floating in the trace. The root span records which prompt versions
ran (builder, reviewer, designer, vitrine), so "compare v4 against v6" is a
metadata filter, not archaeology.

why the frozen benchmark exists: nothing lands without its delta measured.
