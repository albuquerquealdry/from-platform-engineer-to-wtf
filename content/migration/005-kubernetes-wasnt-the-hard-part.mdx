This is the entry I was most confident about before writing it. Self-hosting a model on Kubernetes is
my home turf. Scheduling, resource limits, probes, rollouts, node pools — I've done this for years.

And genuinely, that part took two days. Device plugin, a tainted node pool, a resource request, a
readiness probe that waits for the weights to load. Boring, in the good way.

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
readinessProbe:
  httpGet: { path: /health, port: 8000 }
  initialDelaySeconds: 180   # weights load slowly; be honest about it
  failureThreshold: 30
```

Everything after that was new.

## Assumption 1: a pod is a cheap unit of capacity

It isn't. My entire scaling instinct is built on pods being small, fast and disposable. Add replicas,
absorb the traffic, scale back down.

Here a replica takes three to five minutes to become ready, because it has to pull a very large image
and load weights into VRAM. By the time the new pod is serving, the traffic spike is over.

<Callout type="broke">
  My HPA worked exactly as configured and was completely useless. It scaled up after the incident and
  scaled down just in time for the next one. Reactive autoscaling assumes startup is cheap. Mine
  costs four minutes.
</Callout>

## Assumption 2: utilisation means what I think it means

`nvidia-smi` showed 95% utilisation and I was pleased with myself for about a day. That number means
"a kernel was running", not "the device was doing useful work". Batch size 1 pegs it just as happily
as batch size 32, at a fraction of the throughput.

The number I actually needed was requests served per GPU-hour, which no default dashboard gives you.
Once I measured that, continuous batching in the serving layer roughly tripled throughput on
identical hardware — no infrastructure change at all.

## Assumption 3: cost is an infrastructure line item

The variable that dominated cost turned out to be `max_tokens` in an application config, not anything
in my Terraform. Someone raised a default, output length grew, GPU-seconds per request grew with it.

Nothing in my capacity planning has ever been driven by an application constant. It rearranged my
mental model of who owns cost here.

## What I learned

The gap wasn't Kubernetes. It was that my heuristics assume elastic, cheap, fast-starting, stateless
units — and inference is none of those:

| My instinct | Reality here |
| --- | --- |
| Scale reactively on CPU | Provision ahead; startup is minutes |
| Utilisation ≈ efficiency | Throughput per GPU-hour is the only real metric |
| Cost lives in infrastructure | Cost lives in prompt and output length |
| Replicas are interchangeable | Batching behaviour makes them very much not |

The platform skills transferred completely. The *judgement* built on top of them did not, and that's
a much less comfortable thing to discover.

## What's next

I keep arriving at the same conclusion from different directions: I can build and run these systems,
but I still can't tell you if they're any good. Next block of work is evaluation — properly, not
forty rows in a spreadsheet.

Still migrating.
