The definition I kept hearing was "DevOps for machine learning". I accepted it for two years because
it let me keep nodding in meetings. Having now actually built one end-to-end pipeline, I think that
definition is true in the way "a database is a file" is true.

## What I already knew

The CI/CD half maps cleanly. Build, test, package, promote, deploy, observe, roll back. I've built
that machinery a dozen times. If MLOps were only that, this journal would be very short.

## What I didn't know

In a normal service, the deployable artifact is code, and code is deterministic. In ML you have
*three* things that can change independently, and any one of them can silently change behaviour:

| Artifact | Versioned by | Changes behaviour? | Usually versioned in practice |
| --- | --- | --- | --- |
| Code | Git | Yes | Always |
| Model weights | Registry / hash | Yes | Usually |
| Data | ...good question | Absolutely | Almost never |

That third row is the whole discipline. My mental model of "deploy" assumed the artifact was the only
input. Here, the artifact is a *function of data I didn't version*, produced by a training run I
can't reproduce, evaluated on a set that may have drifted.

<Callout type="broke" label="Where my model of the world broke">
  I rolled back a deployment to a known-good commit and got different predictions than the previous
  week. The code was identical. The model file was identical. The upstream feature table had been
  backfilled. Nothing in my rollback story covered that.
</Callout>

## The shape of the thing

Once I stopped trying to force it into a deploy pipeline, the shape got clearer:

The bottom edge — monitoring feeding back into data and evaluation — is the part that has no real
equivalent in the services I run today. My services degrade loudly. Models degrade quietly, while
every dashboard stays green.

## What I built

A deliberately small pipeline, so that nothing could hide behind a framework: a scheduled job that
pulls a snapshot, trains a trivial model, writes metrics, and refuses to promote if a metric drops.

```python
# promote.py — the entire "MLOps" part that actually mattered
THRESHOLD = 0.02  # allowed regression, decided by argument with myself

def promote(candidate: Metrics, incumbent: Metrics) -> bool:
    if candidate.auc < incumbent.auc - THRESHOLD:
        log.warning("blocked: auc %.4f < %.4f", candidate.auc, incumbent.auc)
        return False
    if candidate.rows_trained < incumbent.rows_trained * 0.9:
        log.warning("blocked: training set shrank, suspect upstream")
        return False
    return True
```

Fourteen lines. It has already blocked two promotions, one of which was a genuine upstream problem
that no alert of mine would have caught.

## What I learned

MLOps isn't DevOps plus GPUs. It's DevOps where the definition of "correct" is statistical, the
artifact has a hidden dependency on data, and the failure mode is *quiet*. Everything I know about
reproducibility still applies — I just had one fewer input in my model of the system.

## What's next

user, and find out which of my assumptions about latency survive contact with an LLM.
