By part 6 the platform was fully built: living design system, component kit,
worked examples, surgical edits, honest images. One variable remained untested —
the model itself. Our builder had always run on the house frontier model. Is that
quality worth its price, or could a challenger do the job at a fraction? We
stopped guessing and ran a tournament.

## Getting challengers into the ring

Rule one of the platform hasn't changed since part 1: every model call goes
through the corporate proxy, where cost accounting, rate limits, and audit live.
So the challengers came in the honest way: a GitOps merge request to the proxy's
config repo (three new entries routed to an external aggregator, each with its
real price mirrored into the model info so accounting doesn't book them as
free), an API key written into the cloud secret manager, synced by the external
secrets operator, and twenty minutes later three new names in the model catalog
— selectable per module from the admin screen, no code changes, no restarts.

The lineup: our incumbent frontier model as the reference, plus **DeepSeek v4
Pro**, **GLM 5.3**, and **Kimi K2.7 Code** — three models the community keeps
naming for UI code generation, at list prices between a quarter and a tenth of
the incumbent's.

## One judge, frozen rules

The methodology decision that makes the rest of this entry trustworthy: **the
visual critic never changes**. The Designer agent — the one that screenshots the
real preview and critiques it — stays pinned to the incumbent model in every
round, for two reasons. Mechanically, it needs vision, which the challengers
don't all guarantee. Methodologically, a fixed judge is a fixed ruler: each
model's work gets measured by the same eyes, including the incumbent judging its
own output with no home advantage.

Everything else is frozen too: same user prompt (a support-tickets dashboard for
a public-sector team, realistic data required, critical tickets must pop), same
agent prompts from the registry, same component kit, fresh project per round.
Only the builder-side model varies.

## The rounds

**The incumbent** set the bar: $0.286, 154 seconds, and the finest product
instinct of the four — it added a first-response-time column per ticket that
nobody asked for and every support team wants.

## The anatomy of a disqualification

GLM's 15 minutes decompose into three independent problems. Throughput: 47
tokens/second, half of DeepSeek's. Verbosity: 42k output tokens, a tournament
record. And a pathology: its worst single call took **305 seconds to emit 105
tokens** — not slow generation, a provider-side stall. The per-agent timelines
extracted from the traces make it visceral: Kimi finishes its entire run before
GLM's builder gets a fifth of the way through.

<Callout type="broke">
  List price is not operating cost. GLM has the cheapest input of the four
  ($0.05/M) and finished as the most expensive challenger, because output is
  $3.39/M and it writes 42k tokens per run. A model's cost is the product of
  price <em>and</em> its consumption profile — chatty models burn their own
  discount. Only a benchmark that runs the real workload reveals this.
</Callout>

## The verdict that acquitted the models

Across all four rounds, the code Reviewer approved on first pass and the build
gate never fired — no model broke the project. And across all four rounds, the
visual critic rejected the first attempt with the **same core complaint**: the
"new ticket" form wasn't visible or reachable enough. Four different models,
four different architectures, one identical failure.

<Callout type="learned">
  When one model fails an instruction, suspect the model. When every model
  fails the same instruction, convict the prompt. Our rule said "a button that
  opens a form" — all four read that as permission to bury the form. That's not
  a capability gap; it's our ambiguity, now queued as a prompt fix. A
  multi-model benchmark doubles as a prompt linter: it separates "the model is
  weak" from "we wrote it badly" — which single-model testing never can.
</Callout>

The judge also earned its keep beyond the refrain: it caught a dev-server error
overlay covering Kimi's screen (invisible to code review, which approved), and
flagged redundant KPIs on the incumbent's attempt. Three entries ago we built
the critic to police beauty; it keeps policing truth.

## Standings and what happens with them

Two real challengers emerged. **Kimi K2.7 Code**: the incumbent's speed at 37%
of its cost. **DeepSeek v4 Pro**: the lowest cost on the board, if you'll trade
four minutes for it. The recommendation now sitting with the team: promote one
of the two to default builder under observation — the fixed judge stays on the
incumbent, which keeps quality control at frontier level while the heavy
lifting gets cheap — and rerun this exact tournament when the next heavyweight
(the model family everyone cites as the aesthetics ceiling) lands behind the
proxy, where its path already exists.
