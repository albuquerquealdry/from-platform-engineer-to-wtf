Part 5 gave the agent taste. This entry gives it hands: the ability to edit a file
without rewriting it, to delete what shouldn't exist, and to put real images on a
page without playing roulette with the internet. It also contains the most
instructive failure of the project so far: one where every individual agent did
its job and the *system* still shipped garbage.

## Few-shot: the technique everyone ranks first

Every analysis of the leaked prompts from the big app-builders converges on one
claim: examples move quality more than any rule. Our prompt was 100% rules. So the
builder's prompt (v6 in the registry) gained a complete worked example (theme
tokens plus a fully composed page, with the reasoning annotated) and five
right/wrong pairs (raw color vs. token, div-modal vs. Dialog, `alert()` vs.
toast...).

One methodological decision worth stealing: the example is deliberately in a
**parallel domain** (a subscriptions tracker), not the domain of our frozen
benchmark prompt. If the example matched the benchmark, the model would copy
instead of generalize, and every measurement after that would be flattery. The
prompt doubled in size (from ~7.7k to ~15.3k characters), which is a real cost
on every single call; that delta is part of what the next benchmark round exists
to judge.

## The day the jury convicted the innocent

Then a user asked for something off-script: a product landing page for a phone
that doesn't exist, "with lots of visual elements and photos for marketing." What
happened next is the best systems lesson of the week:

1. The Builder did the **right** thing: no image generator existed, so it shipped
   a CSS illustration of the device.
2. The code Reviewer **rejected it**: "missing real photos of the device; there's
   only a CSS illustration."
3. The fix round obeyed the reviewer: it went hunting for image URLs on the open
   internet. One loaded: a stock mockup watermarked with the *wrong phone
   model*. Two came back as broken frames.
4. The visual critic flagged the brand inconsistency but let the broken frames
   through, and the run closed as the most expensive generation to date.

<Callout type="broke">
  No model misbehaved. The Builder followed policy, the Reviewer enforced a
  standard, the fix round obeyed the review. The failure was that the policies
  disagreed: nothing stated whether a page without photos was a defect or the
  correct behavior of a platform that had no safe way to produce photos. When two
  agents in one crew hold contradictory rulers, their cooperation manufactures
  rework. Alignment of judgment criteria is architecture, not prompt flavor.
</Callout>

The same day, all three rulers were rewritten to agree: external image URLs are
forbidden (they break, vanish, and carry watermarks); a CSS/SVG composition in
place of a photo is *correct* behavior, never a defect; and the visual critic
gained automatic vetoes (broken frame, watermark, product name inconsistency).

## Images, the honest way

Banning hotlinks doesn't answer the user's real need: pages want pictures. The
answer became a small pipeline where every image **becomes a local file in the
workspace** (the origin only matters at fetch time, never at runtime):

Three facts made this sweeter than planned. First, the corporate proxy's catalog
turned out to already expose an **image generation model**: the external
dependency we'd filed as "pressure on the proxy team" had quietly resolved
itself. A generated hero image costs on the order of a thousand tokens: cents.
Second, when the stock-photo provider we wanted paused new API keys, a keyless
Creative-Commons catalog filled the slot the same hour, because the download
architecture makes the *origin* interchangeable. Third, the daemon's fetch
endpoint validates content-type and size and accepts `data:` URLs, so generated
images and downloaded ones travel the exact same audited path.

## Scalpels: editing without rewriting

Since part 3, every small edit ("change the button color") rewrote entire
files. That's expensive (a one-line change cost about as much as a lodge
website's full edit round) and risky in large files. The leaked prompts are
explicit about this: *prefer search-replace; write-file is for new files or full
rewrites.*

The daemon gained three actions, and the Builder three tools:

- **replace-in-file**: literal, single-occurrence match. Zero matches is an
  error ("reread the file"); two matches is an error ("add context"). The tool
  refuses to guess: ambiguity is the caller's problem, by design.
- **remove-file**: files only. And it closes a debt from part 3's sabotage test:
  when a file dies, its fossilized compile errors are scrubbed from the error
  ring, so the gate stops failing runs over a ghost.
- **fetch-asset**: the image pipeline above.

The prompt demoted `write_file` to "new files and genuine rewrites." The
acceptance measurements (token cost of a small edit before/after, and a replay
of the sabotage test where the agent can finally *delete* the planted file) are
queued; numbers land in the next entry.

<Callout type="learned">
  Tool semantics are prompt engineering by other means. "Replace this exact
  unique string" teaches the model precision at the API boundary, where it can't
  be ignored the way a prompt suggestion can. The best rules are the ones the
  runtime enforces.
</Callout>

## Where this leaves the platform

The quality roadmap born from the leaked-prompt analysis is now fully built:
living design system, first-impression protocol, mature component kit, worked
examples, surgical edits, honest images. What remains is measurement: the
frozen-benchmark rounds that say what each step actually bought, in dollars and
in looks.
